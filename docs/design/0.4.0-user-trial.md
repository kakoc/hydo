# A new user's trial of 0.4.0's features

This page records one trial of the features that are new since 0.3.4, made as a developer who
had not used hydo before. The trial ran on 2026-11-17 on an Apple Silicon Mac (M2 Pro), so every
run used the Mac engine. The tester learned only from what a user sees: `README.md`,
`docs/ONBOARD.md`, `hydo guide <topic>`, the `--help` output, and the examples' own `RESULTS.md`
files where the guide points to them.

The maintainers asked for an honest report before they decide on the 0.4.0 release. The user's
words for what to check were these four: rust, usefulness, api, and experience. Each section below gives what
was done, the time, what worked, each friction in order with the exact message, and a verdict.
The last section answers whether 0.4.0 is ready for a new user.

## The setup: hydo built from `main`

`cargo build --release -p hydo` at `c1d78449` took 1 min 55 s. The program calls itself
`hydo 0.3.4`. `hydo doctor` then reported 8 failed checks, because a checkout has no guest
kernels or engine programs, and it named the fix:

```text
doctor: get them with   hydo setup --get 0.3.4   (the 0.3.4 release into ~/.hydo/versions/0.3.4; this hydo then uses it), or install a release and run its bin/hydo.
```

That command failed:

```text
hydo setup: this points ~/.hydo/bin/hydo at hydo 0.3.4; it pointed at hydo 0.3.1. Every shell of this user that finds hydo there runs 0.3.4 from now on; `hydo setup --get 0.3.1` points it back
hydo setup: hv/hvm/explore/out/Image-explore-containers: is a pinned asset of this hydo, but the release's SHA256SUMS does not list it (this bin/hydo belongs to another release)
hydo setup: the release is damaged or incomplete, and hydo setup repairs no file: unpack the release again (check the download) and run its install.sh
```

The download was not damaged. The tree pins a guest kernel that no published release has. The
first line also said that the link `~/.hydo/bin/hydo` now points at 0.3.4, but setup stopped
before it changed the link. The trial went on with the 0.3.4 release tree, the guest kernel
`Image-explore-containers` built from the tree, and the tree's `hydo`, `hydo-build` and
`hydo-hvm` copied in by hand. `hydo doctor` still printed 6 failed checks for that tree, and
every run worked.

A user of the published 0.4.0 release does not meet this, when the release carries the kernel. A contributor, or anyone who tries
`main` before a release, cannot boot a guest without the hand-made tree.

## 1. A web app on the Mac (`hydo guide web-apps`)

### What was done

The web-shop example (`hydo/onboard/examples/web-shop`) was copied to a scratch folder. Its
`build.sh` ran `npm ci` and the two builds of the app. Then these commands ran:

1. `hydo build hydo.yaml`, the shop with its Playwright tests and the app's fixed build.
2. `hydo run "disk=none | run"`, the clean schedule.
3. `hydo run "disk=none | run H=api.add_item@1-2:delay=1000"`, the guide's schedule for the
   flaky test.
4. `hydo explore --seeds 1-8 --protocol-faults`, then `hydo report` and `hydo report --html`.
5. `hydo build hydo-walk.yaml`, the walk (`browser.explore`) over the app's buggy build.
6. `hydo run --image hydo-out/explore-ob-web-shop-walk-arm64.cpio.gz "disk=none | run"`.
7. `hydo explore --image ... --seeds 1-10 --protocol-faults`, then `hydo report`,
   `hydo report --html` of the exploration and of one recording replay.

### The time

| step | wall time |
|---|---|
| `build.sh` (npm, both builds of the app) | 4 s |
| `hydo build hydo.yaml`, with the 1 GB Playwright image fetched | 1 min 56 s |
| the clean run (OK, 3 tests passed) | 19 s |
| the flaky test's schedule (VIOLATION) | 14 s |
| the exploration of 8 seeds with the tests | 3 min 31 s |
| `hydo build hydo-walk.yaml` | 69 s |
| the clean walk (OK) | 33 s |
| the exploration of 10 seeds with the walk | 29 min 54 s |

The first useful result, the flaky test failing on purpose, came 6.5 minutes after the start
of `build.sh`.

### What worked

- The flaky test failed exactly as the guide says, with the test's own assertion as the verdict:
  `VIOLATION [browser.tests_pass] The test "shop.spec.ts › adds two products to the cart" failed
  after 0.4 s: ... Expected: "2" / Received: "0"`. The clean schedule passed.
- The exploration with the tests found one failure at seed 7 and replayed it to the same
  fingerprint: `H=api.get_order@0-1:reset` fails the test named `places an order`.
- The walk needed no test. Its exploration found the planted order-page bug at seed 7, shrunk to
  7 actions per step: `The page /orders/o6 left a promise rejection unhandled during the test
  "walk step 3": HttpError: HTTP 502 for /api/orders/o6`.
- The recording replay of that finding kept its verdict and left a video, a Playwright trace, a
  screenshot, and `repro.spec.ts`. The test is short and readable, with the fault as one
  `page.route` handler. `hydo report --html` of the replay folder shows the video.
- The build of the walk image after the first build took 69 s, and each walk run took 10 to 30
  seconds.

### Frictions, in order

1. The explorer's first lines say that it draws no fault, and then it draws `H=` faults:

   ```text
   hydo explore: the faults it draws: none of the project's kinds. --new-faults adds pauses and clock jumps.
   ```

   The project's `faults:` is `[protocol, clock, pause]`, and `--protocol-faults` was given.
2. The plain report numbers steps from 1, and the schedule numbers them from 0. The schedule
   `H=api.get_order@0-1:reset` reads `During step 1, the outside service api ... resets the
   connection`, and the engine's own line says `PROTOCOL FAULT 1 on before step 0`. In the walk's
   problem 2, `H=api.get_order@3-4:reset` reads `During step 4`, the finding says `during the
   test "walk step 3"`, and `repro.spec.ts` puts the fault under `// step 3`.
3. One problem's page contradicts itself. Its headline is `Web-shop failed your check while an
   outside service misbehaved`, and its advice is `A test that fails only under these conditions
   depends on timing`. The section below says `The test program failed, with no fault that
   explains it.` The fixed build fails this test by design when the order cannot be read, as the
   example's `hydo.yaml` says.
4. The walk's exploration printed nothing for 30 minutes, because its output was not a terminal.
   Most of the time went to shrinking. Two failures took about 150 shrink runs.
5. The walk's problem 1 has a recording that does not show the failure. The explorer said:

   ```text
   hydo: the walk of disk=none dseed=975835de1c9756ce | run I=813a9e4ce991433d,n3,... ended otherwise (HYDO-ORACLE: OK invariants=5 held ...) with recording on: video, trace and repro.spec.ts in hydo-out/explore-walk/replays/rec-1/screens
   ```

   The problem itself, `The page / showed the busy element .spinner ("Loading products…") for
   10.2 s ... it showed no error..`, has no fault left in its schedule. The tester cannot tell
   from the report whether it is a bug of the app or of the walk. The verdict also ends in two
   periods.
6. The exploration's web page neither shows nor links the recordings. The guide says `hydo report
   --html of that folder shows the video and the test`. Only `hydo report --html` of
   `replays/rec-2` showed the video; the exploration's page had no `<video>` and no link to
   `replays/`.
7. The walk exploration did not find the planted double order in 10 seeds. The guide promises
   nothing about 10 seeds, so this is a note and not a fault.

### Verdict

Useful. A flaky Playwright test failed on every run of one schedule. A walk found a frontend
bug without a test. Both worked on the first try from the guide. The report's words are
the weak part: the step numbers disagree, one page contradicts itself, and one recording shows a
passing run under a failing problem.

## 2. Value history and value properties (`hydo guide values`)

### What was done

The Blnk example (`hydo/onboard/examples/blnk`) was copied to a scratch folder. Its `build.sh`
built the 14 programs with Go 1.27.3 and checked each against its pin, and
`hydo/fetch-images.sh` fetched PostgreSQL and Redis. Then these commands ran in `hydo/`:

```sh
hydo build hydo-values.yaml --arch arm64 --set arch=arm64
hydo run "disk=none | run"
hydo inspect values <run dir> --changes --text
hydo inspect values <run dir> --broken --text
hydo inspect values <run dir> --key c33 --text
hydo report <run dir>
hydo report --html <run dir>
hydo repro --regressions
```

### The time

| step | wall time |
|---|---|
| `build.sh`, with a warm Go module cache | under 2 minutes |
| `fetch-images.sh` | about 30 s |
| `hydo build hydo-values.yaml` | 52 s |
| `hydo run "disk=none | run"` | 35 s |
| `hydo repro --regressions` (3 regressions) | 77 s |

After the programs were built, the fetch, the build and the run took about 2 minutes together,
and the run gave the first useful result: the broken value property.

### What worked

- The image had the sha256 that the example's `RESULTS.md` names, `62d83259…`: the build is
  reproducible across machines.
- The run without faults broke the value property for the same 3 of 66 keys as the guide shows,
  with the same lines. Every business rule held in that run, so only the property saw the bug.
- `hydo inspect values --changes` showed 4 keys with a change. Key `c31` is a good lesson: its
  coalesced copy had 0.0, but its decision saw 50.0, so it did not break the property.
- `hydo report <run dir>` says in plain words what broke, why it is worth a look, and the next
  command. It is the clearest output of the whole trial.
- The three saved regressions gave their expected verdicts.

### Frictions, in order

1. `hydo guide values` uses the Blnk example in every snippet, and it never names the example's
   folder or says how to build it. The build steps are only in the header comment of
   `hydo/hydo-values.yaml`. The build needs Go 1.27.3 and network access, which the guide does
   not say.
2. The build command needs the architecture twice, `--arch arm64 --set arch=arm64`. The second is
   a parameter of the manifest. Without it, the image would carry the amd64 programs.
3. The fingerprints differ from the recorded ones. On the same image, `RESULTS.md` records
   `f52b32d3577045db` for `disk=none | run` and `ddb6f1730f6854ea` for the regression
   `overdraft-limit-concurrent-draws`. This tree gave `2cdb1283669c5c9b` and `f0cfabf31eb1f68b`.
   The verdicts were the same. A reader who compares fingerprints, as the page invites, sees a
   failed reproduction.
4. `hydo inspect values --key c33` prints `1 keys, 1 of them with a change; 1 shown`.

### Verdict

Ready. This is the feature that made the trial's strongest case. The guide's output came out
line for line, and the report explains a value property to a reader who has never seen one.
The guide needs the example's path and build steps.

## 3. hydo in CI (`hydo guide ci`)

### What was done

A throwaway git repository in the scratch folder held the release's Redis example as `hydo/`,
a `hydo/ci.yaml` with `engine: hvm` and seeds 1-20, and a `.gitignore`. It had two commits on
`main`, and a branch `relax-fsync` with one commit that set `appendfsync everysec`. Nothing was
pushed. These commands ran:

```sh
hydo ci run --base main                                  # on relax-fsync
hydo ci comment hydo-ci
hydo ci run --mode push --out ../ci-main-run             # on main
hydo ci record ../ci-main-run --store ../hydo-history --report
hydo ci record hydo-ci --store ../hydo-history --report
hydo ci record hydo-ci --store ../hydo-history --branch pull/1 --report
hydo ci page --store ../hydo-history
```

### The time

| step | wall time |
|---|---|
| `hydo ci run --base main`: both builds, 56 runs, 4 replays | 69 s |
| `hydo ci run --mode push` on `main`, image from the cache | 25 s |
| `record`, `page`, `comment` | under 1 s each |

### What worked

- The branch's run failed with exit status 1 and 2 new findings, each proven by a replay on the
  base: `VIOLATION [redis.acked_writes_survive] key k:# lost` under `disk=cut ... | run C=20`,
  and `VIOLATION service cannot recover (committed data unrecoverable) (redis)`. The base passed
  both schedules.
- `comment.md` is a good pull-request comment. It shows each finding's minimal schedule, the
  replay command with "after `hydo build`", the first difference from the base, and the
  `hydo ci accept` line.
- `junit.xml` has one failed test per finding, with the schedule, the key, and the replay command.
- The `main` run reused the base's image from the cache.
- The history page is one file that opens without a network. It has a timeline per branch, the
  runs, and a link to each run's report.

### Frictions, in order

1. `hydo ci record` of a pull request's run without `--branch` stops and points to a file that a
   user of a release does not have:

   ```text
   hydo: hydo ci record: a pull request's run is recorded only with --branch NAME (the history is the line of a branch: pushes to it and its scheduled runs; docs/design/ci.md section 4.3)
   ```

2. The history page's headline is `No open problem in redis`, and the page then lists two findings
   marked `Open` on `pull/1`. The headline counts only `main`, and it does not say so.
3. The page gives both runs the time `2026-11-17 16:55:53 UTC`, the time of the recording. The
   two runs ran 3 minutes apart, and each finding's `first saw it` has the same recorded time.
4. `hydo ci --help` lists `--backend kvm|hvx`, while the guide's `engine:` takes `hvm` too.
5. The report names a replay command without `--image`. In a repository, the user must first
   build the image in the project folder, which only the comment says.

### Verdict

Useful, with two page errors. The whole loop, from a change to a comment that names the cause,
took about a minute on a laptop. Fix the history page's headline and times before teams read the
page.

## 4. `hydo fuzz` on a small Rust crate (`hydo guide fuzz`)

### What was done

The crate was `glob-match` 0.2.1, a glob matcher of one file with a function
`glob_match(glob, path) -> bool`. Its README documents the syntax. The tester wrote seven property
functions in the crate's `#[cfg(test)]` module, as the guide's section "Write a property
function" shows. Each had `input ... like` lines and `// hydo: ensures result`:

| property | what it says |
|---|---|
| `literal_matches_only_itself` | a glob without special characters matches only the same text |
| `star_is_one_segment` | `*` matches a text if and only if it has no `/` |
| `globstar_matches_all` | `**` matches every path |
| `escaped_text_matches_itself` | a glob that escapes each character matches the text |
| `questions_match_each_char` | one `?` per character matches a text without `/` |
| `brace_of_two_words` | `{a,b}` of two words matches exactly those two words |
| `captures_agree` | `glob_match_with_captures` matches when `glob_match` does |

Then `hydo fuzz glob-match-0.2.1 --list`, `hydo fuzz glob-match-0.2.1`, replays with `--input`,
and `hydo fuzz --vm` of one function ran.

### The time

`--list` took 1 s. The first run of all seven functions took 16 s: 4 held and 3 broke. Each
replay took about 5 s. `hydo fuzz --vm` of one function took 38 s on the Mac engine. That time
includes three schedules and the shrink.

### What worked

- Each broken property came with its smallest input and a replay command:

  ```text
  hydo: contract broken: glob-match::tests::questions_match_each_char ensures result (src/lib.rs:564) on 466 of 1000 calls
  hydo:   smallest input (1 shrink step): text = "日"
  hydo:   again: hydo fuzz 'glob-match-0.2.1' --fn 'tests::questions_match_each_char' --input 'text = "日"'
  ```

- Two of the three breaks are candidate bugs of `glob-match` 0.2.1. Neither was checked against
  its issue tracker, and nothing was posted:
  - `?` matches one byte, not one character. `?` does not match `日`, and `???` does. The README
    says that `?` matches any single character.
  - A brace with an empty word never matches the empty text: `{foo,}` matches `foo` and not
    the empty text. `{foo,}` stands for `foo` or the empty text.
- The third break was the tester's own mistake, and the shrunk input made that plain at once.
  The escape property broke on `text = "r"`, and the README allows `\` only before special
  characters. After the property escaped only those, it held on 1,000 calls.
- `--show-inputs 4` showed which inputs the `like` lines made.
- `hydo fuzz --vm` ran on the Mac engine and reported the same break, with the note `it failed
  without a fault too: the function or its check is wrong before any fault meets it`. The guide
  says that only hvx had run it.

### Frictions, in order

1. The function under test is a free function, but no comment line can state a property of it
   alone. The language has no call, so every useful property became a test-module function.
   This works, and the guide says so, but the guide's first example states a clause on the
   function itself.
2. `hydo fuzz --vm --help` prints the native help. The guide says `The options are in hydo fuzz
   --vm --help: --schedules N ...`, and the help names none of `--vm`, `--schedules`, `--faults`
   or `--batch`.
3. A run with no fault prints `HYDO-ORACLE: OK invariants=1 held (fuzz.checks: )`, with an
   empty part in the brackets.

### Verdict

Ready for small pure functions. From the first comment line to two candidate bugs took less
than 10 minutes. The API is plain Rust in the crate's own test module, and the reports are
short.

## 5. `hydo guide strategies`

### What was done

The tester read the topic for one type of system, a job queue or a workflow engine, and judged
whether it says what to do first.

### What worked

- The table "Start here" names three techniques for a job queue: kills of the process that holds
  the work, clock steps with the clock audit, and the messages check.
- The three findings below the table say what to do first in every project. Write the generic
  rule first, explore with `--strategy process` first, and run each durability setting at its
  durable value.
- Each entry has the same parts: what it is, what to write, when it fits, what it found, what it
  misses, and the cost. "What it misses" is the most useful part for a newcomer.

### Frictions, in order

1. Every number cites a milestone of `docs/HISTORY.md` or an example's `RESULTS.md`. Neither is
   in the Mac release or the Homebrew install, and "Milestone 291" means nothing to a user.
2. The table does not say which engine each technique needs. `cf=` is hvx only, value
   properties need the Mac or KVM engine, and `--more-faults` is refused on a Mac. A Mac user
   learns this only in each entry's last line.
3. The examples of what to write are other projects' schedules, such as `K=hatchet_engine_1@6+3`.
   The topic does not say how to choose the step and the service for a new system.

### Verdict

Useful. It answers "what first" for a job queue in its first screen. It reads as a summary of
the project's history more than as a guide, because of the milestone references.

## Is 0.4.0 ready for a new user

Almost. Every feature that the trial tried gave its first useful result within minutes, from the
guide alone, and every failure replayed with the same fingerprint. The value property and the CI
loop worked better than expected. The faults are in what hydo tells the user. Several pages state
things that are not true of the run: a step number, an engine's fault list, a headline, and two
times. A new user trusts those words first, so they must be right before the release.

The three fixes that would matter most:

1. **Number the steps the same way everywhere.** The schedule, the plain report, the findings,
   and `repro.spec.ts` must name one step by one number. Otherwise every reader of a report
   looks at the wrong step.
2. **Make the CI history page true.** The headline must count the open findings of every branch
   it lists, or name the branch it counts. Each run must show the time it ran. Otherwise a team
   reads the words `No open problem` over two open findings.
3. **Make the walk's recording and the exploration page agree.** A problem whose recording
   passes must say so on its page, and the exploration's page must link each `replays/rec-<k>`.
   Otherwise the headline web feature hands the user a video of a passing run.

The guides need smaller fixes too. `hydo guide values` must name the Blnk example's folder and
its build steps. The explorer's first line must list the fault kinds it draws. `hydo fuzz --vm
--help` must list the VM options.

caught the friction, and `docs/HISTORY.md` Milestone 301 has the proof runs.

|---|---|---|
