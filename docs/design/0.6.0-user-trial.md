# A new user's trial of 0.6.0's features

This page records one trial of the features that are new since 0.5.0, made as a developer who
had not used hydo before. The trial ran on 2026-11-25 on an Apple Silicon Mac (M2 Pro), so every
run used the Mac engine. The tester learned only from what a user sees: `README.md`,
`docs/ONBOARD.md`, the Mac quickstart, `hydo guide <topic>`, and the `--help` output. The tester
read no source code of hydo and no `RESULTS.md` file of an example.

The maintainers asked for an honest report before the 0.6.0 release. Each section below gives
what was done, the command, the time, what worked, each friction with its exact message, and a
verdict. The section [The frictions, ranked](#the-frictions-ranked) ranks the frictions of all
sections once more, by what they cost. A section near the end describes the bugs that the trial
found in the project under test.

## The setup: the project and the hydo

The hydo was the release build of `main` at `d1931461`. It calls itself `hydo 0.5.0`, because
the version is raised later, and it uses the 0.5.0 release's guest files from `~/.hydo`.
`hydo doctor` printed `doctor: all checks passed`.

The project is NSQ v1.3.0 (`github.com/nsqio/nsq`), a message queue in Go with about 25,000
stars on GitHub. It has two programs:

- `nsqd` takes messages over HTTP (`POST /pub`) and over its own TCP protocol, and hands them
  to consumers. A consumer acknowledges a message with `FIN`.
- `nsqlookupd` tells consumers where the topics are.

NSQ's documentation says that `--mem-queue-size=0` writes every incoming message to disk, so
that only a failure of the operating system or of the disk can lose one. That is the promise the
trial tested. NSQ has no Compose file, so the tester copied the one of nsq.io's Docker page, with
the official image `nsqio/nsq:v1.3.0`, `nsqd`'s data on a volume, and `--mem-queue-size=0`. The
client is a Go program of 420 lines, `nsqc`, written for the trial. It publishes, consumes, drains,
and reads back final states. It records each operation with the Go SDK's history recorder
`hydohist` (`github.com/kakoc/hydo/sdk/go@v0.5.0`). It writes the events of the reactions as
`HYDO-ASSERT` lines to `/dev/console`.

The trial took about 1 hour from the first guide page to the last regression, and the write-up
took longer. About 30 minutes of the hour were explorations. The rest was reading the guide,
writing the client, and reading results.

## 1. `hydo onboard` from a Compose file

### What was done

```sh
hydo onboard
HYDO_FETCH_IMAGE=~/.hydo/versions/0.5.0/bin/hydo-fetch-image sh hydo/fetch-images.sh
hydo build hydo/hydo.yaml --check
hydo build hydo/hydo.yaml
hydo run "disk=none | run"      # twice
```

### The time

| step | wall time |
|---|---|
| `hydo onboard` (the import, `AGENTS.md`, two skill copies) | under 1 s |
| `fetch-images.sh` (one image of 25 MB) | 2.7 s |
| `hydo build` | 28 s |
| one run without faults | 9.5 s |

The clone came at 11:36 and the first run without faults passed at 11:40. The tester had
read the guide for 10 minutes before the clone, and wrote the client in between.

### What worked

- `hydo onboard` found the Compose file, both services, and the language. It wrote a
  `hydo.yaml` with both services, pinned digests, addresses, and the order of the start. It
  printed the next command, with the right path of `hydo-fetch-image`.
- The import said why it added no mount for the volume on `/data`.
- `hydo build --check` printed the resolved declaration of the messages check.
- Two runs without faults printed the same fingerprint, `fp=f929bc3123f1bb43`, and `OK`.

### Frictions, in order

1. The import wrote `data: dirs: [vol/nsqd-data]`, a folder that no service uses. Its own warning
   says that the volume on `/data` was not added, so `nsqd` writes to `/data`. To use the power
   loss of one service (section 6), the tester moved `nsqd`'s data to `/data/vol/nsqd-data` and
   gave it `storage: {dir: vol/nsqd-data, size_mib: 256}` by hand.
2. The workload placeholder names the first service, not the one that takes writes:
   `# TODO: one operation with item $i against nsqlookupd (port 4160)`. In NSQ the writes go to
   `nsqd`.
3. The build wrote 1.6 GB into `.hydo/` beside an image of 33 MB:
   `explore-ob-nsq-arm64-disk.img` (808 MB), `explore-ob-nsq-arm64-data.img` (512 MB), and
   `explore-ob-nsq-arm64-vol-nsqd.img` (256 MB). On a Mac with 11 GB free that mattered. No line
   of the build says which of these files the runs need.
4. `hydo onboard` printed `Next: open Claude Code here and run /hydo:onboard`, but it installed
   the skill as a project folder, `.claude/skills/hydo`. The tester did not check whether Claude
   Code names a skill of that folder `/hydo:onboard`.

### Verdict

Yes, a new user keeps it. The import gave a working start for two services in under a minute,
and every friction cost minutes, not hours.

## 2. `hydo rules scan --kind writes` and `--kind clock`

### What was done

```sh
hydo rules scan --kind writes
hydo rules scan --kind clock
hydo rules scan --kind clock --all
```

Each scan took less than a second over the 107 Go files.

### What worked

- The write scan found the two routes that matter, `POST /pub` and `POST /mpub`, with their
  declarations at `nsqd/http.go:61` and `:62`.
- The clock scan ranked `NewGUID` in `nsqd/guid.go` second, with three clock-step schedules. That
  place holds the trial's second finding: after a step back of the wall clock, a publish to an
  existing topic waits until the clock passes its old value. The blind exploration then found it
  with `T=7:-1265` (the section "What the trial found in NSQ").

### Frictions, in order

1. Every handler of the write scan is the decorator, not the route's function:
   `handler V1 (internal/http_api/api_response.go:49)` for all 20 routes of class `data`. The
   real handlers, such as `s.doPUB`, are on the same line of `nsqd/http.go`.
2. The scan lists none of the TCP protocol's commands (`PUB`, `MPUB`, `DPUB`, `FIN`, `REQ`,
   `TOUCH`), and its output does not say that it read no TCP protocol. `FIN` is how a consumer
   acknowledges a message, and the trial's first finding needs a consumer. `hydo guide rules`
   says that a project's own binary protocol is not read, but the scan's output should say it
   too.
3. The scan joins three programs. The routes of `nsqadmin`, which the Compose file does not run,
   are listed as writes (`DELETE /api/topics/:topic`). A route of `nsqd` and of `nsqlookupd` with
   one path is one entry with `also at nsqlookupd/http.go:46`, although the two are different
   services with different data.
4. `/pub` is entry number 12 of the list, after `/channel/pause` and `/topic/pause`, although
   the guide says that the list puts durable writes first. A pause and a `PUT /config/:opt`
   are classed `data`.
5. The clock scan's schedules for a place in `nsqlookupd` name a placeholder:
   `disk=none | run T=1:-300 K=<database>@2+3`, under the line `Run by nsqlookupd (nsqlookupd)`.
   The service is known, so the schedule could name it.
6. The clock scan's words for `NewGUID` do not match the code: `It compares the time since an
   earlier wall-clock reading with a duration.` The code refuses a new id while the clock is
   behind the last id's time. The place and the schedules were right.

### Verdict

Yes for the clock scan: in under a second it pointed at the place where every publish waits
after a clock step. The write scan is a good checklist for an HTTP API, but on NSQ it named the
wrong handler for every route and missed the protocol that the consumers use.

## 3. A messages check with `acked_outcome` and `effect: recorded`

### What was done

The check in `hydo/hydo.yaml`:

```yaml
checks:
  - id: jobs
    type: messages
    history: jobs
    final: /bin/nsqc drain
    acknowledgement: explicit
    claims:
      delivery: at-least-once
      lease: {ms: 60000}           # nsqd --msg-timeout: an unacknowledged message comes back
      acked_outcome:
        effect: recorded
```

Three commands make the workload: `parallel_driver_pub` publishes one message `m<id>`,
`serial_driver_consume` takes one message, holds it 2.5 s and sends `FIN`, and
`eventually_publish` checks that a publish works again after the faults. The drain takes every
message that is left, with a quiet window of 70 s, longer than `nsqd`'s message timeout of 60 s.
Then it writes one `status` record per sent id. NSQ reports no state per message, so the
read-back takes the consumers' own record: `s=ok` and `f=1` when a consumer sent `FIN` for the
message, `s=info` and `f=0` when none did. The read-back's first version took a receipt as the
final state. The tester changed it after friction 1, so that the claim sees a message that a
consumer received and never acknowledged.

### What worked

- `hydo build --check` accepted `acked_outcome: {effect: recorded}` without `client_errors`, and
  printed the declaration it resolved.
- The first run without faults judged every claim: `no-phantom held judged 24`, `no-loss held
  judged 20`, `acked-outcome held judged 24`.
- The claim `acked_outcome` found what `no-loss` could not. A kill of `nsqd` while a consumer
  held a message lost that message: it never came back to any consumer. The claim broke with
  `m0 was acknowledged and has no final state (no error code)`. The same run's `no-loss` counted
  the message as delivered, because a consumer had received it once.

### Frictions, in order

1. A run whose acknowledged messages were all received once, one of them lost in flight, ends in
   an ERROR whose words are not true:

   ```text
   HYDO-ORACLE: ERROR check jobs.no-loss could not be evaluated: no group that had to receive the acknowledged messages has a drained record: the check's final: drain must write `drained <channel> <group>` when it has read everything
   ```

   The drain had written `HYDO-HIST jobs 100000 ok 77315867161 drained jobs work`. The tester
   suspected the record's time, changed the clock the client reads, rebuilt, and got the same
   ERROR. That cost about 20 minutes. The plain report adds `If the error comes from hydo itself,
   attach the details of this page to a bug report for hydo`, which points the user away from the
   cause. The same ERROR stopped 5 of the 36 runs of the aimed round (section 4).
2. A message that a consumer received, never acknowledged, and that never came back is not a
   loss for `no-loss` with `acknowledgement: explicit`. The guide's drain rule 1 says that such a
   message comes back only when its lease or visibility timeout runs out. So the tester
   expected `no-loss` to judge it. The claim `lease` did not catch it either: `lease held 0 no
   message was delivered again in its group while a lease on it held (0 judged, 0 undecided)`.
   Only a read-back that the tester wrote for `acked_outcome` caught it.
3. For a queue, `acked_outcome` repeats `no-loss` unless the read-back invents a final state.
   NSQ reports none per message. `hydo guide messages` describes the claim for systems that
   answer at once and do the work later, a task queue or a job runner, and gives no example for a
   plain queue. The tester chose "a consumer sent `FIN`" as the final state.
4. The violation's words for a lost message do not fit a queue: `m0 was acknowledged and has no
   final state (no error code)`. The words `(no error code)` say nothing to the reader of a lost
   message.
5. The Go recorder has no call for a record without an invocation, so the drain wrote its
   `drained` line by hand. `hydo guide messages` shows only the Rust SDK's `q.drained`. The Go
   SDK's `hydoassert` documentation says that it writes to `/dev/ttyS0` by default, while `hydo
   guide sdks` says `/dev/console`. The tester wrote the `HYDO-ASSERT` lines by hand to be sure.
6. The clean run judged `no-loss` on 20 of 24 acknowledged sends, with `undecided 0`. No line
   says why 4 sends were not judged.
7. The verdict line names only the first claim, also when it held:
   `checks=3 held (jobs.no-phantom: every delivered message was sent before it was delivered
   (24 judged, 0 undecided))`.

### Verdict

Yes, with care. The claim found a loss that the other claims missed, and that alone is worth it.
A new user who meets the ERROR of friction 1 blames the drain or hydo before the system.

## 4. `hydo explore` and `--reactive-at` on the client's event

### What was done

A blind round, then a round aimed at the consumer's event `nsq.msg_received`, which the client
writes when it holds a message. Both rounds ran first with the client's first version, which
recorded the effect when a consumer received a message. That blind round took 9 min 22 s, and
that aimed grid of 18 cells took 15 s. After the fix of section 3, both ran again:

```sh
hydo explore --seeds 1-20 --strategy process --storage-faults --out hydo-out/blind
hydo explore --reactive-at nsq.msg_received@2 --react-delays 0..2500/500 \
  --react-actions kill,powerloss --seeds 1-36 --out hydo-out/aimed
```

### The time

| round | runs | workers | wall time |
|---|---|---|---|
| blind, process strategy, with storage faults | 20 | 3 | 9 min 26 s |
| aimed, the grid of 18 cells, run twice | 36 | 5 | 1 min 15 s |

A run of this image took 1 s of the engine. The blind round spent 89 % of its workers' busy
time on re-runs and shrinks, and the aimed round 85 %.

### What worked

- `--reactive-at` said exactly what it would do before the first run: `a grid of 18 schedules,
  after nsq.msg_received@2, every 500 ms from 0 to 2500, with kill-nsqlookupd, kill-nsqd and
  powerloss-nsqd. Seed k runs cell k of the grid: seeds 1-18 run it once with the plain workload,
  and seeds 19-36 run it again with each seed's composition.`
- The aimed round found the loss of a message in flight in 15 of 36 runs, and shrank it to one
  reaction: `disk=none dseed=0 | run A=nsq.msg_received:kill-nsqd`.
- The blind round found the loss after a kill without any consumer, and the wait of every
  publish after a clock step back (the section "What the trial found in NSQ"). Every failure
  reproduced with its fingerprint.
- The progress line every 30 s showed the work while the output was not a terminal.

### Frictions, in order

1. The plain report's "See it again" command is the whole failing run for some problems, also
   when the shrink found a smaller schedule. In the first blind round, problem 3 showed
   `K=nsqd@4+3 P=nsqlookupd@12+1 W=5764a73c,p3,q2,r200`, and `hydo report --details` gave the
   minimal schedule `K=nsqd@4+1 W=:p1,r200,...`.
2. A problem of the report of both rounds contradicts itself. Problem 4's title is `Nsq failed
   your check after nsqd lost power and after a clock jump`, and its steps say `After 1 step, nsqd
   loses power on its own`. Its command is the minimal schedule, `T=7:-5062 W=...`, which has
   no power loss.
3. In the first blind round the property table said `jobs.acked-outcome 13 0 PASS`, while seed 2
   failed that claim and was problem 3 of the same report. In the aimed round the table says
   `jobs.acked-outcome 19 4 FAIL`, while problem 1 alone lists 15 runs that failed the claim.
4. The header of the aimed round says `Faults tried: crashes and power losses`, and the same
   report says `Never drawn, though the project allows them: ... power losses of one service
   (--storage-faults draws them)`. The grid drew `powerloss-nsqd` in 12 runs.
5. The report's line `Why it failed: hydo inspect diagnose hydo-out/aimed --problem 2` printed
   one long JSON document, and `--text` printed the same JSON with line breaks. The tester read
   the replay's `one.log` instead.

### Verdict

Yes. `--reactive-at` is the feature that a new user would keep first. It turned a guess about a
window into 36 runs in 75 s, and it found the in-flight loss that 20 blind runs did not. The
report's words about the problems need the fixes of this section.

## 5. `hydo stats` and `hydo report` of several explorations

### What was done

```sh
hydo report hydo-out/blind hydo-out/aimed
hydo report --html hydo-out/blind hydo-out/aimed
hydo stats hydo-out/blind hydo-out/aimed
hydo stats hydo-out/blind
```

### What worked

- `hydo report` of both folders listed 6 problems, each once. Each problem named the rounds and
  the seeds that showed it, for example `in 2 of 2 explorations: 1 (seeds 1, 3, 5, 6, 8, 11,
  12, 13 and 3 more) and 2 (seeds 14, 15, 20, 27, 32 and 33)`. It took 0.4 s.
- `hydo report --html` wrote `hydo-out/blind/report-merged.html` (18 KiB).
- `hydo stats hydo-out/blind` gave the curve, the cost, the faults drawn per kind and target, and
  the estimate, all in plain words: `power losses of one service: 7 of 20 runs; on nsqd 7`.

### Frictions, in order

1. `hydo stats hydo-out/blind hydo-out/aimed` printed only the second folder, `36 first runs
   (random strategy, seeds 1-36)`, with no word about the first. `hydo stats --help` shows one
   `[DIR]`. A user who reads `hydo report A B` in the guide expects `hydo stats A B` to work the
   same way, or to refuse.
2. The aimed round's statistics count its 12 reactions `powerloss-nsqd` as `reactions to events:
   12 of 36 runs; at 1 of the 20 workload steps (not in faults:)`. `powerloss` is in `faults:`.
   The same page then says that power losses of one service were never drawn. The 24 kill
   reactions are counted as crashes, so all 36 runs had a reaction, and the page says 12.
3. Problem 1 of the report of both rounds groups the whole-guest power cut of the blind round
   with the aimed round's power loss of `nsqd` alone, under the title `after a power cut`. Its
   command has `C=20`, which none of the aimed round's runs had. The problem also shows two
   `hydo ci accept` lines with two different keys.

### Verdict

Yes for `hydo report` of several folders. `hydo stats` of one folder is useful; of several
folders it misleads without a warning.

## 6. A power loss of one service from a reaction

### What was done

```sh
hydo run "disk=none | run A=nsq.pub_acked@5+100:powerloss-nsqd"
```

and the grid of section 4 with `--react-actions kill,powerloss`.

### What worked

- The console named the moment and what happened: `POWER LOSS of nsqd at the reaction
  A=nsq.pub_acked@5+100:powerloss-nsqd (/dev/vda5 shut down and mounted again; what was not
  written back is lost)`.
- The grid's power loss 500 ms after a consumer took a message lost all 9 acknowledged
  messages, shrunk to `A=nsq.msg_received@2+500:powerloss-nsqd`. NSQ syncs its files every 2 s,
  and its documentation names an operating system failure as the risk of `--mem-queue-size=0`,
  so the tester takes this loss as documented.

### Frictions, in order

1. The run by hand passed, and nothing said whether the power loss had anything to lose. Linux
   had written NSQ's files back before the loss. The guide says that the plain loss keeps what
   the kernel wrote back, and `:strict` exists only as an `L=` token. The tester expected a
   `powerloss-strict-<svc>` reaction, or a word in the run of how many dirty pages the loss took.
2. The statistics and the report call these reactions never drawn (section 5, friction 2).

### Verdict

Yes. It needed one `storage:` line and no other change, and the grid found its loss at the first
try.

## 7. `hydo save`, `hydo repro --regressions`, and `# params:`

### What was done

```sh
hydo save hydo-out/blind
hydo save hydo-out/aimed
hydo build hydo/hydo.yaml
hydo repro --regressions
```

For `# params:`, the manifest got a build parameter, `memq`, for `--mem-queue-size` (`params:
{memq: "0"}`, with NSQ's default 10000 as the other value). Then:

```sh
hydo build hydo/hydo.yaml --set memq=10000
hydo explore --seeds 1-6 --strategy process --out hydo-out/memq
hydo save hydo-out/memq
hydo build hydo/hydo.yaml                      # memq=0
hydo repro --regressions
hydo build hydo/hydo.yaml --set memq=10000
hydo repro --regressions
```

### The time

| step | wall time |
|---|---|
| `hydo save` of one exploration | under 1 s |
| `hydo repro --regressions`, 5 regressions | 51 s |
| `hydo explore --seeds 1-6` of the `memq=10000` image | 8 min 4 s |
| `hydo repro --regressions`, 6 regressions | 1 min 21 s |

### What worked

- Every saved regression replayed with its expected verdict: `hydo: 5 of 5 regressions as
  expected`. The files carry the verdict, the composition, and the commands' hashes.
- With a `# params: memq=10000` line in a regression, the build of the default image warned:

  ```text
  hydo-build: warning: regression process-clock-VIOLATION-eventually_publish-eventually_publis needs the build parameters memq=10000 (this build: memq=0): `hydo repro --regressions` leaves it out on this image; build its image with `hydo build --set memq=10000` and replay it there
  ```

  `hydo repro --regressions` then printed `SKIP ... not run: it needs the build parameters
  memq=10000 (this image: memq=0)` and `5 of 5 regressions as expected, 1 left out`. On the
  image built with `--set memq=10000` it ran all 6, as expected.

### Frictions, in order

1. `hydo save` of the exploration of the `memq=10000` image wrote no `# params:` line. The
   tester added it by hand. `hydo guide workflow` says that "a saved regression that needs other
   build parameters names them on a line of its file", which reads as if `hydo save` writes it.
   Neither `exploration.json` nor the image's record `explore-ob-nsq-arm64.cpio.gz.json` names
   `memq`. `hydo save --help` and the section "Regressions" of `hydo guide manifest` do not
   mention the line.
2. A regression without the line runs on every build. The 5 regressions found on `memq=0` ran
   on the `memq=10000` image without a word. A regression found on the default build should name
   the default too, when the manifest has `params:`.
3. `hydo save` names a file by its class and the start of its verdict, and keeps the first file
   of a name:

   ```text
   hydo: hydo/regressions/process-VIOLATION-jobs.acked-outcome-of-judged-operations-di.schedule exists, kept
   ```

   So different findings with one check got no file, and only that line said so. Problem 3 of
   the aimed round, the power loss of `nsqd` from a reaction, has no regression. Its filename is
   the one of problem 1, the in-flight loss after a kill. Of the 3 problems of the `memq=10000`
   round, 2 got no file, because files of the `memq=0` build had their names.
4. A build with `--set` writes the same filenames as the default build,
   `.hydo/explore-ob-nsq-arm64.cpio.gz`. Each build replaced the image that the other build
   made, and the reports' replay commands name that path.

### Verdict

Yes. The replay of saved regressions is fast and exact, and the `# params:` check does what it
promises once the line is there. `hydo save` must write the line and must not drop findings
whose names collide.

## 8. The s3 emulator with `durable: true`

NSQ keeps its messages on a local disk and uses no object store, so the trial did not try the s3
emulator.

## What the trial found in NSQ

The trial found three candidates in NSQ v1.3.0 with `--mem-queue-size=0`. Each reproduced with
its fingerprint on the Mac engine. Nothing was posted, and the tester did not search NSQ's issues
for them.

### A kill of `nsqd` loses the messages of a topic's first seconds

- Schedule: `disk=none dseed=0 | run K=nsqd@4+1 W=:p1,r200,cparallel_driver_pub,0.0.0.503389004,1.0.0.1894126023,2.1.0.662703717,3.2.0.938279500,4.3.0.533815299,5.3.0.567436972,9.6.0.750492478`
- Verdict: `VIOLATION [jobs.acked-outcome] 6 of 7 judged operations did not end as the system answered them`. Six messages that `nsqd` answered `OK` were never delivered.
- The fault is a kill of the process, not a power cut, so the page cache keeps every write.
- The cause, read in go-diskqueue v1.1.0: `diskqueue.go` writes its metadata file
  (`<name>.diskqueue.meta.dat`) only at a sync, every 2 s or every 2,500 messages. When `nsqd`
  starts and finds no metadata file, `retrieveMetaData` returns an error that `New` ignores. The
  queue then starts at file 0, position 0, as an empty queue, although the data file holds the
  messages. The check for a data file larger than the metadata says runs only when the metadata
  file exists.

### A kill of `nsqd` loses the message that a consumer holds

- Schedule: `disk=none dseed=0 | run A=nsq.msg_received:kill-nsqd`
- Verdict: `VIOLATION [jobs.acked-outcome] 4 of 4 judged operations did not end as the system answered them: m0 was acknowledged and has no final state (no error code); ...`
- A consumer took `m0` and held it. The kill came before its `FIN`. After the restart `m0` never
  came back, although NSQ promises delivery at least once.
- The cause was not read in the code. The consumer's channel reads `m0` from its disk queue and
  keeps it in memory while it is in flight. A sync of the queue's read position before the kill
  would explain the loss.

### A step back of the wall clock stops every publish to a topic

- Schedule: `disk=none dseed=0 | run T=7:-1265 W=:p1,r100,cparallel_driver_pub+serial_driver_consume,...` (the full line is in the saved regression)
- Verdict: `VIOLATION [eventually_publish] eventually_publish exited rc=1: probe: no publish succeeded within 60 s after the faults`. Every probe ended with `context deadline exceeded`.
- The cause is the place that the clock scan ranked second. `NewGUID` (`nsqd/guid.go:55`) reads
  `time.Now()` and returns `ErrTimeBackwards` while the clock is behind the last id's time.
  `Topic.GenerateID` (`nsqd/topic.go:491`) retries every millisecond until the clock passes it.
  By the code, after a step back of 21 minutes every publish to an existing topic waits 21
  minutes. The run showed that no publish succeeded in the probe's 60 s.

## The frictions, ranked

Each friction is ranked by the time it cost the tester and by how far it led the tester away
from the cause.

1. **A messages check ends in an ERROR that names the wrong cause** (section 3, friction 1). It
   said the drain wrote no `drained` record, while the drain had written it. About 20 minutes
   and one rebuild. If it is not fixed, a new user blames the drain or reports a hydo bug, and
   the run's real loss stays hidden.
2. **`no-loss` does not judge a message that a consumer received and never acknowledged**
   (section 3, friction 2). The tester found the in-flight loss only through a read-back written
   for `acked_outcome`. If it is not fixed, the default claims of a work queue pass a lost
   message.
3. **`hydo save` drops findings whose filenames collide, and writes no `# params:` line**
   (section 7, frictions 1 to 3). 3 problems of two rounds got no file, and one line each said
   `exists, kept`. If it is not fixed, a regression folder looks complete and is not, and a
   regression found on one build runs on another.
4. **A problem's words and its command disagree** (section 4, frictions 1 and 2). The steps
   describe the first failing run, and the command is either that run or the minimal schedule.
   About 10 minutes to compare with `hydo report --details`. If it is not fixed, a user replays a
   noisier run than needed, or looks for a fault that the command does not have.
5. **The property table counts too few failures of `acked-outcome`** (section 4, friction 3).
   If it is not fixed, a reader of the table takes a broken claim for one that held.
6. **`hydo stats` of two folders prints only the second, and the counts of reactions are wrong**
   (section 5, frictions 1 and 2). If it is not fixed, a user takes the cost and the faults of one
   round for both, and believes that power losses were never tried.
7. **The write scan names the decorator as every route's handler and does not say that it read
   no TCP protocol** (section 2, frictions 1 and 2). About 10 minutes to find `doPUB` and the
   protocol by hand. If it is not fixed, the user writes no command for the operations of the
   protocol, here the consumers' `FIN`.
8. **The build leaves 1.6 GB of files beside a 33 MB image, and a `--set` build replaces the
   default image** (section 1, friction 3, and section 7, friction 4). If it is not fixed, a Mac
   with little free disk stops other work, and two builds of one manifest cannot be kept side by
   side.
9. **Smaller ones.** They cost a few minutes each:
   - the import's unused `data.dirs`, and its placeholder against the wrong service;
   - the clock scan's `<database>` for a known service;
   - the Go SDK's missing call for `drained`;
   - `hydo inspect diagnose --text`, which prints JSON;
   - the unexplained 20 of 24 judged sends;
   - the report's title `Nsq` for NSQ.

## Is 0.6.0 ready for a new user

Almost. Every feature the trial tried gave its first result from the guide alone, and each
failure replayed with its fingerprint. In about an hour a tester who had not used hydo found three
candidates in a popular queue. Two of them break the documented promise of
`--mem-queue-size=0` with a plain kill, and one stops every publish after a clock step.
`--reactive-at` and the clock scan did the most for that.

The faults are in what hydo says about a run. A messages check that names the wrong cause, a
property table that counts too few failures, and a `hydo save` that drops findings each make a
new user doubt the right thing. These three fixes would matter most before 0.6.0:

1. **Make the messages check's ERROR true, and judge a received message that never came back.**
   Otherwise the default claims of a work queue miss the trial's in-flight loss, and the ERROR
   sends the user to the drain.
2. **Make `hydo save` keep every finding and write `# params:`.** Otherwise a saved folder of
   regressions misses findings, and a regression runs on a build it was not found on.
3. **Make each problem's words, command, and table row describe one run.** Otherwise the user
   replays one schedule and reads about another.
