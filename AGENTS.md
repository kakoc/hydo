# hydo — project context & handoff

This file is the instruction file for any coding agent working in this repository (the AGENTS.md convention, https://agents.md). `CLAUDE.md` only imports it, so every tool reads the same text. Update this file, never `CLAUDE.md`.

`hydo` is a **deterministic hypervisor**. It runs software so that, given the same inputs, execution is bit-for-bit identical every time, which makes record/replay, snapshots and branch-from-snapshot possible. The project has two engines that share no code: **hvx**, our own VT-x hypervisor kernel module (`hv/hvx/`), which owns the VMCS, and **hvm**, the Apple Silicon engine (`hv/hvm/`) built on Hypervisor.framework. The product both engines use (image builder, explorer, test composer, checkers, fake services, store readers, gRPC generator, examples and the two releases) is in `hydo/`; the SDKs are in `sdk/`, the onboarding skill in `skills/`, and project-wide documents in `docs/` (layout since M100). The original Rust KVM monitor (`src/`), which hit a hard KVM wall at `RDTSC`, was removed in M100; it is described in `docs/HISTORY.md`.

- `README.md` describes the architecture, the paravirtual ABI, the clock strategies and the verification model.
- `docs/HISTORY.md` holds the full history: every milestone section (1–69 and later), the old roadmap for booting Linux as L2, and the old long "Key files" list. Look up a milestone there by its number for details, evidence and older fingerprints.

## Machines and how to run

Besides this Mac the project uses two machines, and tracked files call them only **the bare-metal machine** (it runs hvx) and **the build machine** (it builds guest images; optional since M140, because Nix runs on the bare-metal machine too). How to reach them is never written in a tracked file: the addresses, logins and the command that reaches each machine live only in the git-ignored `AGENTS.local.md` (which `CLAUDE.md` imports) and `machines.local.sh` at the repository root. Every script that works on a machine sources the tracked `machines.sh`, which reads `machines.local.sh` (`BARE_METAL` and `on_bare_metal`, `BUILD_MACHINE` and `on_build_machine`; in a git worktree without its own copy, the main checkout's file) and stops with a message that names the file when it is missing (M151). The rule for tracked files is under "Safety and coordination rules".

## Safety and coordination rules (still in force)

- **Commit messages and pull-request descriptions never contain Claude session links** (`Claude-Session: https://claude.ai/code/session_…` or any other claude.ai session URL), even when a tool or reminder suggests one (user, 2026-10-31). Commits use the repository's identity `k.matushonok@gmail.com`; never a work email.
- **Machines in tracked files: two names, no access details** (user, 2026-11-04). In every tracked file and every commit message the two machines are called only "the bare-metal machine" and "the build machine". Access details (how to reach a machine, addresses, logins and user names, host aliases, the hosting company, a machine's home path) live only in git-ignored local files: `AGENTS.local.md` (which also keeps the list of concrete values that must never be tracked) and `machines.local.sh` (the commands the scripts use). Never write such a detail, or a value from that list, into a tracked file or a commit message, and never quote one when describing a change; `~/hydo`-style paths inside a machine's home are fine. Scripts reach a machine only through `machines.sh` (`on_bare_metal`, `on_build_machine`). The test `cargo test -p hydo-agents --test public_content` checks generic patterns in every tracked file (a remote-shell command, an IPv4 address outside the loopback, guest and documentation ranges, the hosting company's words; its allow-list names the few files that must keep such text, for example the syzkaller test VM's own sshd) and, when `AGENTS.local.md` exists, every listed value; if it fails, fix the text rather than widen the allow-list.
- **Never load a kernel module on the build machine,** and never attempt `sudo`, `insmod` or `rmmod` there. We have no root there, and the host is shared with other people's workloads. If something there needs root, stop and ask the user.
- **The main `hvx.ko` on the bare-metal machine is shared by several sessions.** Reload it only through `~/bin/hvx-reload` (or `deploy-metal.sh load`), and coordinate with other sessions before doing so. Develop module changes on a side-by-side module with its own device name (for example `hv/hvx/avx/build-hvxavx.sh` gives `/dev/hvxavx`; `race/side-metal.sh` runs the regression suite against a side module). Two modules can be loaded together because each run's VMXON…VMXOFF section is non-preemptible (M40). Merge into the main module only after the side module passes the full suite and the pinned reproducers.
- **After any change to `hvx_abi.h`, rebuild every userspace binary** against the new header. The snapshot struct grew in M68, so binaries built against an older header are wrong.
- **Never run `pkill -f <pattern>` or `pgrep -f <pattern>` through a remote shell when the pattern also matches the remote command line itself.** `pkill` then kills your own session, and a wait loop such as `until ! on_bare_metal 'pgrep -f "<pat>"'; do sleep; done` never finishes. Match with `pgrep -x`, a pid file or a done-marker file instead, or put the `pkill` into a script whose path does not match.
- **Every wait loop needs a timeout,** including the wait loops of agents you start.
- **Build guest images one at a time on the build machine,** and copy each to the bare-metal machine before building the next, because the disk fills up.
- **Delete only your own files.** The boxes are shared by several sessions. For anything else, ask the user and name the candidates. Safe-to-regenerate leftovers are `~/hydo/build/rootfs-*-root` trees and `*-ext4.img` / `*-data.img` intermediates.
- **Stop your own background jobs by pid file, never by name.** On the shared box `pgrep -x <script>` matched another session's script with the same name and killed it (2026-10-24). Write each job's pid to a file in your own directory and kill that pid only.
- **Keep existing fingerprints stable.** A new module feature must be opt-in and inert when off, so that every recorded baseline is unchanged; check this with `deploy-metal.sh` and the pinned reproducers before and after.

## Language policy (decided by the user; updated 2026-10-30)

- **Rust is the project language** (user, 2026-10-30). Most of the code should be Rust, and the Rust implementation is the reference for everything. There will be one `hydo` command written in Rust, over one engine interface (hvx on Linux, hvm on the Mac), in a Cargo workspace at the repository root. The Python product layer (explorer, image builder, composer, error logs, history checkers, Compose importer, `hydo guide/skill/init`) was ported to Rust (M101–M106), each port proven identical to the Python version (same schedule strings, same image bytes, same verdicts and fingerprints), and the Python was deleted in M107; its answers live on as the Rust tests' recorded expected outputs. The explorer and the engine runner were ported too: the engine runner is `hydo/crates/hydo-hvx` (M132), in-process by default, and the C `hv/hvx/hvx_explore.c` was deleted in M137; the Mac engine's runner is `hydo/crates/hydo-hvm` (M143), and the C `hv/hvm/hvm.c` and `explore/serve.c` were deleted in M147. Research and measurement scripts were deleted in M108 (each can be restored from git, docs/HISTORY.md M108); the bug benchmark runner was ported (`hydo-bench`).
- **The kernel module stays in C** (`hv/hvx/hvx.c`). Reasons: most of its bugs were about hardware semantics and determinism, which Rust does not prevent; its core is VMX instructions and inline assembly that would be `unsafe` Rust anyway; and a Rust module needs a kernel built with Rust support, which most distribution kernels lack. Its safety net is testing: `hv/hvx/safety/` (`SAFETY.md`, M97).
- **No prose specifications.** Examples and tests are the specification: for example the SDKs share a folder of example files generated by the Rust SDK's tests ("this call writes exactly this line"), and the schedule language is defined by its parser plus example schedules.
- **SDKs:** the Rust SDK is the reference; Go, Python and JavaScript follow it by testing against the shared example files, with frozen scope (assertions, BUGGIFY, history records). A format change starts in Rust. No new SDK languages; code-first test definitions only in Rust (`hydo-test`).
- **A rewrite must be byte-for-byte neutral:** the same fingerprints for the pinned reproducers (`1dc3677fb94053cf`, `ba0aa0612502a1df` since M155, fingerprint epoch 1) and every recorded baseline, the same console and schedule formats. Guest-side programs whose bytes are inside recorded images (for example `hvx_seedrng`, pinned `c2a440c5…`) are NOT rewritten.
- **Go helpers:** none are left in the product: `hydo-world` is Rust since M111, `hydo-grpc-gen` and its client `hydo-grpc` are Rust since M113, and `hydo-read` (with `hydo-check`) since M112. The hand-written module tests and verify harnesses stay in C while they only exercise the module's C ABI.

### The results format (M115)

- One versioned model for what runs and explorations report (crate `hydo/crates/hydo-results`; `hydo/PRODUCT.md` "Where the results are"; experimental until hydo 1.0, additions only from version 1 on). A run directory holds `result.json` (one `run` document: schedule, image path and SHA-256, engine, verdict, fingerprints, findings, the run's property table, error-log analysis, consoles); an exploration directory holds `events.jsonl` (written while it runs: `start`, a `run` record for every run with its `role` — `first`, `rerun`, `shrink`, `minimal`, `error-shrink`, `error-minimal`, `trace`, `probe`, `manual`, `branch` —, `shrink`, `end`) and `exploration.json` (configuration, summary, failures with reproductions, shrinks, error kinds, property table, liveness, freeze-sweep stages). Findings have one shape: `kind` (`invariant`, `assertion`, `history-check`, `error-log`), `id`, `status`, `message`, `details`. Every record has `"v": 1` and a `"type"`.
- Kept as views: `report.md` (made from `exploration.json` by `hydo_explore::md`; `hydo report` prints the same text from the document) and the printed summary line. Kept as inputs or working files, not results: the consoles, `engine.log`, `worker-*.err`, `points.txt` (`--sweep-dry`), the `$HYDO_EXPLORE_CACHE` file. Gone: `run.json`, `runs.jsonl`, `shrink.jsonl`, `report.json`, `errors.json`, `properties.txt`, `sweep-points.jsonl`, `fc-traces.jsonl` (`--fc-traces` reads an `events.jsonl`, or an old file), `fc-adaptive.json`, `consoles/<tag>.errors.json`, `<tag>.checks.log`/`.checks.txt`, `consoles-merged/` and the compiled `hydo_assert_report` (the property table is Rust now, byte-identical).
- Readers ignore unknown fields and record types and skip records of other versions (`hydo_results::reader`, tests `hydo-results/tests/reader.rs`); `hydo report`, `hydo repro`, `hydo save`, `hydo errors list|accept` and `hydo-bench depth1map` read through it. Schema `hydo/schema/results-v1.json` (generated; `tests/schema.rs` fails when it differs, and when it is not an additive change of `hydo/schema/released/results-v1.json`, the last released one, so far M115's); examples recorded from real runs in `hydo/schema/examples/results/v1/` (`tests/examples.rs`: they parse, validate and cover every record type, finding kind and main run role). `hydo-explore/examples/legacy_check.rs` maps every value of the old files to the new documents (M115's proof; `--convert` moved the CLI test fixtures).
- **One additions-only check for every format (M148):** `hydo/crates/hydo-schema-compat` (`check(released, now, &Rules)`, a dev-dependency of the three format crates, so no format crate depends on another) compares a released schema with the generated one; the project, results and agent-protocol schema tests all use it, and M114's and M115's two checkers are deleted. One rule set (the crate documentation says why each rule is what it is; `tests/rules.rs` is the table of schema changes with their verdicts) and one per-format option, who reads: `Readers::Current` (the project format: only hydo reads a project, an older hydo refuses what it does not know on purpose, so a widening passes) or `Readers::Released` (results and the agent protocol: readers built for the released schema read what is written now, ignoring unknown fields and root alternatives and nothing else, so a known place may not widen); `Rules::open_enum` names places whose enum may still gain values (the agent's refusal code, kept as text by the host, and command fields, gated by hello features). Always refused: a removed or renamed key, a new or newly required key, a lost type kind or enum value, a changed default, const, format or pattern, a tighter bound, a closed object, an inserted, removed or reordered variant inside a value, a removed root alternative, a reference turned inline or back. Always allowed: notes, new optional keys (also in closed objects), opening a closed object, new root alternatives anywhere, renamed and unreferenced definitions.

### The image records (M155, user decision 2026-11-05)

- **Why:** an image built today must still run, and reproduce, after hydo is upgraded, so every image records what shapes its runs but is not inside it. Crate `hydo/crates/hydo-image` (format and lookup), `hydo/PRODUCT.md` "An image keeps working after hydo is upgraded".
- **Inside the image:** `/etc/hydo/image.json` (next to `/etc/hydo/control`), canonical JSON (sorted keys, no spaces, one newline), `"v": 1`, `"type": "image"`: `arch`, `epoch` (the fingerprint epoch), `kernel` (`file`, `sha256`, `version`, `cmdline`: the kernel by sha256, the rest for people) and, on x86_64, `initrd` (`file`, `sha256`). Nothing that changes with every release is in it (a version there would move every fingerprint at every release). Written by `hydo-build` (`src/record.rs`) for both architectures; the arm64 netns image also keeps M99's `/etc/hydo/kernel`.
- **Next to the image:** `<image file>.json` (`"type": "build"`, written by `hydo build`): the image's and (arm64) the data disk's sha256, a copy of the image record, `hydo.version` and `hydo.commit` (the commit comes from `git rev-parse HEAD` at compile time, or from the git-ignored `hydo/COMMIT` in a tree copied without `.git`), the manifest's path and sha256, and the services' Docker/OCI image digests. Schema `hydo/schema/image-v1.json` (both records), released copy `hydo/schema/released/image-v1.json` (M155's), checked by `hydo-image/tests/schema.rs` with `hydo-schema-compat` (`Readers::Released`).
- **The fingerprint epoch** (`hydo_image::EPOCH`, 1 since M155): increase it by one in the same commit as any change of an engine, the host controller, the agent pin or the guest kernels that moves a recorded fingerprint, that is, at every re-baseline (docs/REBASELINE.md gets a section naming the new epoch; the crate documentation says the same). Runs of one epoch compare fingerprints exactly; across epochs only verdicts. A run, exploration or explorer-cache entry without an epoch (before M155) counts as epoch 1.
- **The kernel at run time** (`hydo_engine::image::boot_files`, used by `hydo run`/`repro`, the explorer and hydo-bench on both platforms): with a record, the kernel (and the x86_64 initramfs) is looked up by sha256 among the files with a known kernel name in the default kernel's directory and the release's `guest/` or the tree's `build/` (`hydo_image::kernels::KNOWN`, the four pinned files, checked against both `assets.sha256` by `tests/kernels.rs`); `kernels::obtain` is the empty plug-in point for a later store or download. Missing: "<image> was built for the guest kernel <file> (Linux <version>, sha256 <hex>), which this hydo (<version>) does not have (looked in <dirs>). The image was built by hydo <version>, commit <hex>. Install hydo <version>'s guest kernel (the file <file> with that sha256) into one of those directories, or rebuild the image with this hydo (hydo build)." An image without the record boots today's choice (the default, or M99's `/etc/hydo/kernel`) with "warning: <image> has no /etc/hydo/image.json (built before Milestone 155): it boots this hydo's default guest kernel; rebuild it with hydo build to record the kernel it needs".
- **Epochs compared:** `hydo repro <run dir|exploration>` and `hydo repro --transcript` say REPRODUCED/DIFFERENT by fingerprint within the epoch; for another epoch they print "the recorded fingerprints are from fingerprint epoch N and this hydo (<version>) is at epoch M: fingerprints from another epoch are not comparable, so the verdicts are compared instead" and SAME VERDICT/DIFFERENT by verdict class. `hydo run` notes when the image was built at another epoch. The explorer's `$HYDO_EXPLORE_CACHE` answers only from entries of its own epoch (each entry carries `epoch`).
- **Results format additions (format 1):** `Run.epoch`, `Start.epoch`, `Exploration.epoch` (the running hydo's epoch); `Image.epoch`, `Image.kernel`, `Image.built_by` (`version`, `commit`), `Image.manifest_sha256`, `Image.services` (`service`, `image`, `digest`, `config_digest`), filled from the two records (`hydo_explore::results::image_of`). The running hydo's version was already `hydo_version`.

### Linux determinism, clocks and the module

- hvx boots real Linux 6.6.35 deterministically: two boots from scratch and every branch-from-snapshot reach a bit-identical full state (console, snapshot, guest RAM, disk). Current boot baselines: no-disk `7a5559028ffbf52c`, with-disk `36583d533d7c989b` (M34). Guest RAM can be up to 3 GiB, below the MMIO hole, and 3 GiB boots are identical; `hvx_bigram_test` checks every page of a 3 GiB guest (M28, M36).
- The default clock counts VM exits: the virtual TSC advances by a fixed step per exit. The **PMU branch clock** (`HVX_VM_PMU_CLOCK`) counts the guest's retired conditional branches in hardware and gives a tick every period (default 2^20 branches, 2 ms of guest time) at an exact instruction (M33). Since M65 the branch counter is frozen while the firmware handles a System Management Interrupt; before that fix, SMIs (which fwupd causes) shifted ticks and caused rare fingerprint differences. Without `tsc=reliable` on the guest command line or the PMU clock, a heavy guest can livelock.
- VM flags (`struct hvx_config.flags`), all off by default: bit 0 `IDLE_HEARTBEAT` (a synthetic tick when the guest idles with nothing armed, M27), bit 1 `X86_64_V2` (M31), bit 2 `PMU_CLOCK` (M33), bit 3 `PAUSE_EXIT` (every `PAUSE` exits and moves the clock, M34), bit 4 `PT_TRACE` (M40), bit 5 `SMP_SCHED` (M66), bit 6 `SMP_BOOT` (M69), bit 7 `X86_64_V3` (AVX/AVX2/FMA/BMI and XSAVE for x87, SSE and AVX only, M68). On the side module `hvxgc` only (M138, not in the main module yet): bit 8 `HOSTCALL` (the host-call port) and bit 9 `DIRTY_LOG` (the dirty-page log), with the ioctls `HVX_RESET_VM`, `HVX_GET_DIRTY` and `HVX_HC_GET`/`PUT`/`GET_STATE`/`SET_STATE` (numbers 64–69) and the exit reason `HVX_EXIT_HOSTCALL`; the main module ignores the two flags and refuses the ioctls, which the engine detects.
- Timing controls for exploring thread interleavings: seeded tick jitter `HVX_SET_TJITTER` (M43), a shorter tick period and inserted extra ticks `HVX_SET_XTICK` (M49), a power cut at the k-th disk FLUSH `HVX_SET_FLUSHCUT` (M56), and the disk's volatile write cache saved and restored through `HVX_GET/SET_UNSYNC` (M43 addendum).
- Code coverage: Intel Processor Trace of the guest (`HVX_SET_PT`, tools in `hv/hvx/pt/`, libipt) gives exact per-instruction coverage; tracing on or off gives identical fingerprints (M40).
- The module's safety net (M97, `hv/hvx/SAFETY.md`): the debug kernel (Linux 6.8.12 with KASAN, kmemleak, UBSAN, lockdep, KCOV) boots in a nested VM on the build machine and runs the deploy-metal suite, three Linux boots and the reproducers (33 pass, 6 PMU tests skip, 0 splats, 0 leaks). syzkaller (`b498adee`) fuzzes `/dev/hvx` with guest programs (`syz_ext_hvx_guest`). Nine module bugs were found and fixed on `main` (a NULL dereference, two heap overflows from snapshot or unsync state, two interrupts-off CPU hangs a guest can cause, a UBSAN shift, an mmap use-after-free, an OOM deadlock, unchecked PT filter MSRs); guest RAM and disk pages are now charged to the caller's memory cgroup and fail with ENOMEM instead of OOM-killing. The fixed module, built as a side module, gives all 33 recorded fingerprints on the bare-metal machine. The main module on the bare-metal machine has had these fixes since 2026-10-30. M140 ran main's module with M138's code under a debug kernel on the bare-metal machine itself (`hv/hvx/safety/onbox/`, booted once with kexec): the whole suite, the explorer, the host-call port and in-place reuse gave their normal-kernel values and no KASAN, UBSAN, lockdep or kmemleak report.
- The Rust KVM monitor (`src/`, which could not get past Linux's `RDTSC` calibration under stock KVM and is why hvx exists) was removed in M100; its baselines and results are in `docs/HISTORY.md`.

- **Not built:** copy-on-write VMs from a snapshot and a read-only root shared between VMs (open item 36).

### Devices and fault injection

- Devices: a 16550 serial port with input (`HVX_PUT_INPUT`), an emulated x2APIC and IOAPIC, a virtio-blk PCI disk (device 3, MSI-X, a page-array image of up to 4 GiB mapped zero-copy into userspace) and a virtio-net PCI device (device 4, scripted receive with `HVX_PUT_RX`, captured transmit with `HVX_GET_TX`). Every device is inert unless attached (M18–M24, M28).

Network faults (`HVX_SET_NET_FAULT`) are drop, delay, corrupt, duplicate and reorder (M24).

### The explorer

- **The hvx engine is Rust and runs in-process (M132; the default since M137, which deleted `hv/hvx/hvx_explore.c`):** `hydo/crates/hydo-hvx` is hvx_explore.c ported function by function (hand-written `hvx_abi.h` types checked against the header by a C probe, hvx_boot.h's recipe byte for byte, `parse_sched` against the C one's recorded answers on 23,351 inputs, `tests/golden/parse_sched_c.txt`). - **Adaptive freeze sweep (M92):** `--sweep freeze --fc-adaptive` sweeps the manifest's `freeze_match:` streams (or, without them, every `--fc-stride`-th packet, default 8), then every packet in a ±`--fc-window` window (default 16) around each failure on the frozen service's links, widened until the failing band is mapped. ### Several virtual CPUs

- With `HVX_VM_SMP_SCHED` and the PMU clock, one `HVX_RUN` runs every vCPU in turns of exactly Q guest branches (or seeded lengths), on one shared clock, and stops only at clean points. `HVX_GET/SET_SCHED` carry the scheduler state (M66).
- With `HVX_VM_SMP_BOOT`, real Linux starts the other CPUs with INIT and STARTUP IPIs and boots on 2, 3 and 4 vCPUs, identically across boots and branches: 2 vCPUs `6584c954c2839491`, 3 `e1a2bb0dd744a9ab`, 4 `1dfafae6887e3a01` (`hv/hvx/hvx_smp_boot_verify.c`, M69). Device interrupts are routed by destination.
- Tests in `deploy-metal.sh`: `hvx_sched_pmu_test` (snapshot `73a465516c4e0094`), `hvx_sched_race_test` (grid `8cb7c61a2393f44e`), `hvx_sipi_test` (`eef5c1ebd4df2e7d` / `c8d015ab3b57252d`), `hvx_sched_sweep_test 2000` (`39971eed9c2f35fe`) and the 2-vCPU boot.
- The explorer takes `--vcpus N` and `--turns`, and `hvx_stack_verify` takes `HVX_VCPUS`; so does `hydo-bench run` (`hydo/knownbugs/sqlite/hunt.py` did; it was deleted in M108). Measured value so far (M74): on the benchmark's race defects and the SQLite WAL bug, several vCPUs found nothing that one vCPU with concurrent clients or tick jitter misses, at about 3× the cost per run; each turn end costs about 0.8 ms of host time, about 0.49 ms with the opt-in margin 160, and burst turns (M85, side module only so far) make dense switching affordable on average. ### Bugs found so far

- In our own order service: a failed cache write failed an order that was already published (M38, fixed in M39); and a duplicate under overlapping retries, a panic on the shared Redis connection, and a crash that forgot which sends had an unknown outcome (M50, all fixed).
- In the stack configuration: with the MySQL binary log off, a commit was visible before its redo fsync finished, found only by the k-th-flush cut (M58, fixed by the binary log in M63); and Kafka's default 7-day retention deleted acknowledged orders after a large forward clock jump (M63, fixed with `log.retention.ms=-1`).
- Upstream: etcd 3.5.5 issue 14685 (member revisions diverge after an online defrag and a crash), found without being told and absent in 3.5.6 (M60); both symptoms reproduce on the `-nq` image (M77, M78).
- Upstream, a known bug found blind (M141): NATS 2.10.22 deletes a whole JetStream stream when every node stops at once shortly after the stream was created (Jepsen's NATS analysis 3.1, nats-server issue 6888, fixed in 2.10.23 by PR 5700): 14 of 50 process-strategy schedules, the first at seed 1, shrunk to one publish and a power cut; also by process crashes alone (reactions); 2.10.23 and 2.12.1 pass. The default `sync_interval` (two minutes) loses acknowledged messages at a power cut on every release (Jepsen 3.4, documented by NATS), `sync_interval: always` does not.
- Upstream, aimed: the SQLite 3.51.2 WAL-reset corruption, reproduced under hydo once a workload restarted the WAL often and its seed was fixed (only timing varied); it passes on 3.51.3 (M85). A blind hunt has not found it: under hydo the workload restarts the WAL 10–70 times less often than natively (M52, M49, M74, M85).
- Upstream, in the order service's Kafka client: franz-go v1.17.1 (issue 1484) lets the idempotent producer acknowledge a record it never wrote, so after a long Kafka pause an acknowledged order is missing from Kafka (M129's agent-only difference, explained in M133). Fixed for the manifest-built images by franz-go v1.22.2 (M135): `disk=none dseed=0 | run P=kafka@14+16`, which lost order 15 on M129's agent control, passes on the new agent control twice (`a41a29598b2738ea`). ## Useful tools and references

- Check a change on the real system, not only by reading code: `hv/hvx/deploy-metal.sh` on the bare-metal machine, or the Mac backend's `hydo` (`hydo/dist/mac/`).
- Review changes to the determinism engine with special care, and keep the baseline fingerprints above passing.
- To onboard a project, follow the hydo onboarding skill (`skills/hydo-onboard/SKILL.md`, an Agent Skills folder that any agent can read; `.claude/skills/` and `.agents/skills/` hold symlinks to it). Check it with `cargo test -p hydo-agents --test skill_check -- --nocapture` after a change (M108).
- For kernel and VMX work there is no ready-made helper: use the Intel SDM Vol. 3C (VMX chapters), the KVM source, and "Hypervisor From Scratch".
